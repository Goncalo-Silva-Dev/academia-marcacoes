O caminho de uma marcação

  1. A Ana abre salaodarita.pt. O browser pede a página ao servidor.
  2. O servidor (Python) lê os serviços na base de dados e devolve uma página HTML.
  3. A Ana escolhe "Corte", dia 3, às 10:00, e carrega em Confirmar. O browser envia esses dados.
  4. O servidor confirma que a hora ainda está livre, grava a marcação na base de dados e responde "Marcação confirmada".

Cada ida e volta chama-se um pedido HTTP. Pedir uma página é um pedido GET; enviar um formulário é normalmente um POST. A resposta traz um código de estado: 200 (correu bem), 404 (não existe), 500 (o servidor teve um erro).

Anatomia de um endereço (URL)

Enquanto estás a construir a app, o servidor corre no teu próprio computador, no endereço http://127.0.0.1:5000. Só tu o vês. Quando estiver pronta, passa para um servidor na internet (Parte 5, etapa 9).

Git e GitHub: nunca perder trabalho

O Git tira "fotografias" do teu projeto. Se estragares alguma coisa, voltas à última fotografia boa. O GitHub guarda essas fotografias na internet.

Experimenta

Estás na pasta do projeto, que já tem um app.py. Segue as tarefas. Usa o botão por baixo do terminal para "editar" o ficheiro, como se tivesses mudado código no VS Code.

Publicar no GitHub

  1. Cria uma conta gratuita em github.com.
  2. Carrega em New repository, dá-lhe o nome marcacabelo, escolhe Private e cria (sem marcar mais nada).
  3. O GitHub mostra-te uns comandos. Na pasta do projeto, corre:
git remote add origin https://github.com/O-TEU-UTILIZADOR/marcacabelo.git
git branch -M main
git push -u origin main

Da primeira vez, abre-se uma janela para entrares na tua conta do GitHub. Depois disso, sempre que fizeres commits novos basta git push.

O ritmo de trabalho: mudas código → testas → git add . → git commit -m "o que fizeste" → git push. Faz commits pequenos e frequentes, sempre que algo funciona.

Funções

Uma função é uma receita com nome: recebe ingredientes (parâmetros), faz alguma coisa e devolve um resultado com return.

Escreves a receita uma vez e usas quantas vezes quiseres. Em vez de repetir a conta do preço em dez sítios, crias formatar_preco e chamas formatar_preco(1500). Defines com def, terminas a linha com : e o corpo da função leva 4 espaços à frente.

return não é o mesmo que print. O print só mostra no ecrã. O return entrega o valor a quem chamou a função, para ser guardado ou usado noutra conta. Os testes verificam o que a função devolve. (A palavra pass significa "ainda não faço nada" e serve para deixar a função vazia.)

Erros, validação e a primeira API

Um servidor recebe dados de qualquer pessoa. Tem de verificar tudo e nunca rebentar com um erro.

Apanhar erros com try / except

Algumas operações podem falhar, por exemplo converter "abc" em número. Com try/except dizes ao Python: "tenta isto; se der este erro, faz antes aquilo".

Como funciona uma API

1. Pedido

O browser envia, por exemplo, POST /api/marcacoes com os dados em JSON.

2. Flask

Liga esse URL a uma função Python, que valida os dados e grava a marcação.

3. Resposta

Devolve JSON e um código de estado: 201 criado, 422 dados inválidos…

Uma boa prática: põe a lógica em funções simples (fáceis de testar, como estas) e deixa o Flask só a ligar os fios.

criar_marcacao(dados) devolve um par (corpo, estado): ({"erros": ...}, 422) se houver erros, ou ({"ok": True, "cliente": ..., "hora": ...}, 201) se estiver tudo bem.

A fonte nº 1 de bugs em apps de marcações. Uma marcação às 10:00 tem de continuar às 10:00 depois da mudança da hora.

Evitar marcações duplicadas

  
Duas clientes veem o mesmo slot livre às 10:00 e carregam em "Confirmar" no mesmo segundo. O que acontece?

  
Este é o problema clássico da condição de corrida (race condition). Verificar "está livre?" e depois inserir são dois passos; entre eles, outro pedido pode passar à frente. Testes manuais quase nunca o apanham. Em produção, num sábado de manhã, acontece.

A solução em três camadas

  

    
1. Base de dados
A restrição EXCLUDE ... WITH && é a garantia final. Nenhum bug na aplicação consegue contorná-la.

    
2. API
Apanha o erro de violação e responde 409 Conflict com uma mensagem clara.

    
3. Frontend
Ao receber 409: "Esse horário acabou de ser ocupado", recarrega os slots e deixa escolher outro.

Segurança e multi-cliente (SaaS)

  
Numa app para vários salões, o pior bug possível é um salão ver os clientes de outro.

  
Os riscos principais

  

    
🔓 IDOR / fuga entre tenants
GET /marcacoes/57 devolve a marcação 57 sem verificar se pertence ao salão do utilizador. Solução: toda a query filtra por tenant_id da sessão, nunca de um parâmetro do pedido.

    
💉 Injeção de SQL
Nunca concatenes texto em SQL. Usa sempre parâmetros (:nome) ou um ORM.

    
🤖 Abuso e spam
Bots a encher a agenda com marcações falsas. Rate limiting por IP/telefone, confirmação por SMS/email para novos clientes, CAPTCHA invisível.

    
🔑 Contas do painel
Passwords com hash (argon2/bcrypt), cookies HttpOnly + Secure + SameSite, proteção CSRF, 2FA para donos.

    
🔗 Links de cancelamento
Token aleatório longo (secrets.token_urlsafe(32)), nunca o ID sequencial. Quem tem o link pode cancelar, por isso tem de ser impossível de adivinhar.

    
📜 RGPD
Dados mínimos, consentimento para marketing separado, possibilidade de apagar o cliente, apagar dados antigos automaticamente.

  

  
Isolar tenants de forma sistemática

  

  
Nível extra: o PostgreSQL tem Row Level Security. Defines uma política USING (tenant_id = current_setting('app.tenant_id')::int) e a própria base de dados esconde as linhas dos outros salões, mesmo que te esqueças de um WHERE.

Páginas com templates

  
Em vez de devolver texto solto, vais devolver páginas HTML a sério, com estilo, e com os serviços do salão.


Escrever HTML dentro do Python seria uma confusão. O Flask usa templates: ficheiros HTML com "buracos" que o Python preenche. A linguagem dos templates chama-se Jinja:


No templateFaz


{{ s.nome }}Escreve o valor de uma variável


{% for s in servicos %} … {% endfor %}Repete para cada elemento da lista


{% if … %} … {% endif %}Mostra só se a condição for verdadeira


{{ preco | euros }}Passa o valor por um "filtro" (uma função Python)


{% extends "base.html" %} e {% block %}Reaproveita a moldura comum a todas as páginas


A estrutura do projeto


marcacabelo/
├── app.py
├── requirements.txt
├── static/
│   └── style.css        ← o CSS
└── templates/
    ├── base.html        ← a moldura (cabeçalho, CSS)
    └── inicio.html      ← a página inicial


Os nomes das pastas templates e static têm de ser exatamente estes: é onde o Flask os procura.


Os ficheiros


O render_template junta o template com os dados. O @app.template_filter cria o filtro euros que usaste na Parte 1.


O url_for('static', filename='style.css') gera o endereço certo do CSS. O {{% block conteudo %}} é o buraco onde cada página põe o seu conteúdo.




Não precisas de perceber todo o CSS agora. Vai mudando cores e tamanhos para veres o efeito.


Com o servidor a correr (flask --app app run --debug), recarrega a página.
